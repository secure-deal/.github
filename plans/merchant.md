# Merchant role redesign plan

## Проблема

Текущая модель `merchant` работает как внешний продавец: самостоятельная регистрация через OTP, редактируемые профиль и пароль, банковские и платёжные данные, прямая собственность на товары с количеством на каждую строку. Целевая модель сохраняет название `merchant` в коде/API, но меняет его смысл на внутреннего менеджера склада — сотрудника, создаваемого администратором. Товары также необходимо разделить на общий каталожный товар и собственность на запасы, специфичные для склада.

## Подтверждённые решения

- Пока сохраняем наименование `merchant` в backend/API/frontend; сначала меняем семантику.
- Цена товара остаётся на общем `product`.
- Данные, специфичные для склада, хранят только количество остатков.

## Наблюдения по текущему состоянию

- Merchant-аутентификация в backend самообслуживаемая: `merchant/auth/register` создаёт merchant, склад по умолчанию, пароль и сессию через OTP-флоу.
- Профиль merchant по-прежнему содержит поля в стиле продавца, такие как `bank_user_id`, `payout_account`, `store_name` и `activity_category`.
- В merchant-panel всё ещё есть публичная страница `/register` и экран самостоятельной смены пароля.
- Admin-panel сейчас отображает список/детали/блокировку merchant, но не создаёт их.
- Хранение товаров всё ещё завязано на merchant: `products.merchant_id`, `products.quantity` и `products.warehouse_id` связывают каталог и остатки в одной записи.

## Предлагаемый подход

1. **Переосмыслить роль merchant как управляемый сотруднический доступ**
   - Заменить саморегистрацию на создание merchant-аккаунтов администратором.
   - Сохранить вход merchant в merchant-panel, но переключить учётные данные на логин/пароль, выдаваемые администратором.
   - Убрать самостоятельное управление логином/паролем со стороны merchant.
   - Где нужно, заменить поля merchant, ориентированные на продавца/выплаты, на поля сотрудника/менеджера склада.

2. **Разделить каталожный товар и складские остатки**
   - Сохранить глобальную/общую таблицу каталога `products` для переиспользуемой идентичности товара и общих цены/контента.
   - Добавить таблицу складских остатков (например, `warehouse_products` / `warehouse_stock`), связывающую `product_id + warehouse_id + quantity`.
   - Перенести правила вида «merchant может удалять только из своих складов» на уровень записей остатков, а не глобального удаления товара.

3. **Перенести создание merchant в admin-panel**
   - Добавить backend-эндпоинты для админа и UI в admin-panel для создания merchant-аккаунтов и назначения одного или нескольких складов.
   - Генерировать или принимать логин/пароль в админском флоу и показывать их один раз для передачи сотруднику.
   - Переделать страницы списка/деталей merchant в админке под семантику менеджера склада, а не продавца маркетплейса.

4. **Переработать merchant-panel вокруг управляемых остатков**
   - Удалить публичный маршрут регистрации и связанные хуки/формы/тексты.
   - Удалить UX смены пароля и любые флоу логина/профиля, предполагающие самообслуживание merchant.
   - Перепроектировать UX создания/редактирования товара так, чтобы merchant мог:
     - искать по общему каталогу товаров,
     - переиспользовать существующий товар,
     - выбирать склад,
     - задавать только количество складского остатка,
     - создавать новый глобальный товар только если в поиске нет совпадений.

5. **Обновить зависимую бизнес-логику**
   - Заменить чтения/записи, использующие `products.quantity`, на запросы к складским остаткам.
   - Пересмотреть флоу резерва/списания заказов, списки товаров merchant, проверки удаления складов, аналитику, админскую статистику и любые фильтры merchant/product, которые всё ещё завязаны на `products.merchant_id`.
   - Определить, какие исторические/отчётные представления остаются в скоупе merchant, а какие переходят в скоуп склада, и затем консистентно обновить SQL и ответы API.

## Этапы реализации

1. **Проектирование домена и схемы**
   - Определить целевые поля merchant и учётные данные для авторизации.
   - Спроектировать схему «общий товар vs складской остаток» и миграции.
   - Спланировать миграцию/бэкфилл данных из текущих merchant-owned товаров в общие товары и строки остатков.

2. **Backend auth и создание через админа**
   - Удалить/деактивировать возможности саморегистрации merchant и смены пароля merchant.
   - Добавить флоу создания merchant-аккаунта администратором.
   - Обновить контракты auth/session/profile для merchant в сторону семантики внутреннего сотрудника.

3. **Рефакторинг складской части в backend**
   - Переработать merchant products, warehouses, orders и admin merchant/product запросы для работы через складские остатки.
   - Добавить поиск по общим товарам и флоу привязки товара к складу.
   - Сохранить slug-ориентированную идентичность товара и правила редактирования контента общего товара.

4. **Изменения в admin-panel**
   - Добавить UI создания merchant и UX передачи учётных данных.
   - Обновить подписи, фильтры и информационные блоки в списке/деталях merchant под семантику менеджера склада.

5. **Изменения в merchant-panel**
   - Удалить `/register`.
   - Удалить UI смены пароля.
   - Обновить тексты и формы логина/профиля.
   - Пересобрать управление товарами вокруг общих товаров и корректировок остатков по складам.

6. **Проверка и rollout**
   - Добавить/обновить интеграционное покрытие для auth merchant, созданных админом, и поведения складских остатков.
   - Перегенерировать frontend API-клиенты после изменений backend-контрактов.
   - Подготовить корректировки миграций/сидов перед rollout.

## Заметки и риски

- Это сквозное изменение, затрагивающее backend, admin-panel, merchant-panel, SQL-миграции, сгенерированные API-клиенты и, вероятно, флоу заказов/остатков.
- `products.quantity` и `products.merchant_id` — самые сильные точки структурной связанности, они повлияют не только на CRUD-экраны.
- Инвалидация кэша при удалении/блокировке merchant сейчас в ряде admin merchant путей предполагает `user:active:${merchantId}`; это нужно пересмотреть при старте реализации, так как ключи auth-кэша недавно стали role-aware.
- Существующие merchant reviews/disputes/analytics могут концептуально всё ещё ссылаться на «merchant/store»; по этим отчётным поверхностям нужно принять явное решение во время реализации, а не молча переиспользовать их под новый смысл.
