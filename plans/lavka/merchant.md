# Manager role redesign plan

## Проблема

Текущая модель `merchant` работает как внешний продавец: самостоятельная регистрация через OTP, редактируемые профиль и пароль, банковские и платёжные данные, прямая собственность на товары с количеством на каждую строку. Целевая модель отказывается от понятия `merchant` в пользу понятия `manager`: это внутренний управляющий складом, сотрудник, создаваемый администратором. Один `manager` отвечает только за один склад. Товары также необходимо разделить на общий каталожный товар и собственность на запасы, специфичные для склада.

## Подтверждённые решения

- Переходим от понятия `merchant` к `manager` в домене, UI, API и коде.
- Один manager может быть назначен только на один склад.
- Цена товара остаётся на общем `product`.
- Данные, специфичные для склада, хранят только количество остатков.

## Наблюдения по текущему состоянию

- Merchant-аутентификация в backend самообслуживаемая: `merchant/auth/register` создаёт merchant, склад по умолчанию, пароль и сессию через OTP-флоу.
- Профиль merchant по-прежнему содержит поля в стиле продавца, такие как `bank_user_id`, `payout_account`, `store_name` и `activity_category`.
- В merchant-panel всё ещё есть публичная страница `/register` и экран самостоятельной смены пароля.
- Admin-panel сейчас отображает список/детали/блокировку merchant, но не создаёт их.
- Хранение товаров всё ещё завязано на merchant: `products.merchant_id`, `products.quantity` и `products.warehouse_id` связывают каталог и остатки в одной записи.

## Предлагаемый подход

1. **Заменить роль merchant на управляемый manager-доступ**
   - Заменить саморегистрацию на создание manager-аккаунтов администратором.
   - Сохранить вход manager в панель управления складом, но переключить учётные данные на логин/пароль, выдаваемые администратором.
   - Убрать самостоятельное управление логином/паролем со стороны manager.
   - Заменить поля merchant, ориентированные на продавца/выплаты, на поля сотрудника/менеджера склада.
   - Закрепить правило: один manager назначается только на один склад и не управляет несколькими складами одновременно.

2. **Разделить каталожный товар и складские остатки**
   - Сохранить глобальную/общую таблицу каталога `products` для переиспользуемой идентичности товара и общих цены/контента.
   - Добавить таблицу складских остатков (например, `warehouse_products` / `warehouse_stock`), связывающую `product_id + warehouse_id + quantity`.
   - Перенести правила вида «manager может удалять только из назначенного склада» на уровень записей остатков, а не глобального удаления товара.

3. **Перенести создание manager в admin-panel**
   - Добавить backend-эндпоинты для админа и UI в admin-panel для создания manager-аккаунтов и назначения ровно одного склада.
   - Генерировать или принимать логин/пароль в админском флоу и показывать их один раз для передачи сотруднику.
   - Переделать страницы списка/деталей manager в админке под семантику менеджера склада, а не продавца маркетплейса.

4. **Переработать manager-panel вокруг управляемых остатков**
   - Удалить публичный маршрут регистрации и связанные хуки/формы/тексты.
   - Удалить UX смены пароля и любые флоу логина/профиля, предполагающие самообслуживание manager.
   - Перепроектировать UX создания/редактирования товара так, чтобы manager мог:
     - искать по общему каталогу товаров,
     - переиспользовать существующий товар,
     - работать только со складом, назначенным этому manager,
     - задавать только количество складского остатка,
     - создавать новый глобальный товар только если в поиске нет совпадений.

5. **Обновить зависимую бизнес-логику**
   - Заменить чтения/записи, использующие `products.quantity`, на запросы к складским остаткам.
   - Пересмотреть флоу резерва/списания заказов, списки товаров manager, проверки удаления складов, аналитику, админскую статистику и любые legacy-фильтры merchant/product, которые всё ещё завязаны на `products.merchant_id`.
   - Определить, какие исторические/отчётные представления переходят в скоуп manager, а какие переходят в скоуп склада, и затем консистентно обновить SQL и ответы API.

## Этапы реализации

1. **Проектирование домена и схемы**
   - Определить целевые поля manager и учётные данные для авторизации.
   - Зафиксировать связь manager со складом как ограничение «ровно один склад на manager».
   - Спроектировать схему «общий товар vs складской остаток» и миграции.
   - Спланировать миграцию/бэкфилл данных из текущих merchant-owned товаров в общие товары и строки остатков.

2. **Backend auth и создание через админа**
   - Удалить/деактивировать возможности саморегистрации manager и смены пароля manager.
   - Добавить флоу создания manager-аккаунта администратором.
   - Обновить контракты auth/session/profile для manager в сторону семантики внутреннего сотрудника.

3. **Рефакторинг складской части в backend**
   - Переработать manager products, warehouses, orders и admin manager/product запросы для работы через складские остатки.
   - Добавить поиск по общим товарам и флоу привязки товара к складу.
   - Сохранить slug-ориентированную идентичность товара и правила редактирования контента общего товара.

4. **Изменения в admin-panel**
   - Добавить UI создания manager и UX передачи учётных данных.
   - Обновить подписи, фильтры и информационные блоки в списке/деталях manager под семантику менеджера склада.

5. **Изменения в manager-panel**
   - Удалить `/register`.
   - Удалить UI смены пароля.
   - Обновить тексты и формы логина/профиля.
   - Пересобрать управление товарами вокруг общих товаров и корректировок остатков по складам.

6. **Проверка и rollout**
   - Добавить/обновить интеграционное покрытие для auth manager, созданных админом, ограничения «один manager — один склад» и поведения складских остатков.
   - Перегенерировать frontend API-клиенты после изменений backend-контрактов.
   - Подготовить корректировки миграций/сидов перед rollout.

## Заметки и риски

- Это сквозное изменение, затрагивающее backend, admin-panel, manager-panel, SQL-миграции, сгенерированные API-клиенты и, вероятно, флоу заказов/остатков.
- `products.quantity` и `products.merchant_id` — самые сильные точки структурной связанности, они повлияют не только на CRUD-экраны.
- Инвалидация кэша при удалении/блокировке merchant сейчас в ряде admin merchant путей предполагает `user:active:${merchantId}`; это нужно пересмотреть при старте реализации, так как ключи auth-кэша недавно стали role-aware.
- Существующие merchant reviews/disputes/analytics могут концептуально всё ещё ссылаться на «merchant/store»; по этим отчётным поверхностям нужно принять явное решение во время реализации, а не молча переиспользовать их под новый смысл.
